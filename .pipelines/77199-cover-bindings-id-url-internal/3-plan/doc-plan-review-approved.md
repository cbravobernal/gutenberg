# Doc Plan Review

## Verdict: approved

## Summary

The doc plan is tight, well-scoped, and correctly identifies the single documentation surface that needs human-edited updates (the Block Bindings reference guide at `docs/reference-guides/block-api/block-bindings.md`). The four tasks (add table row, add Cover-specific notes, add Pattern Overrides example, add CHANGELOG entry) cover every author-facing surface the code phase will affect. Key claims verified against the repo:

- `docs/reference-guides/block-api/block-bindings.md` exists with the "Compatible blocks and their attributes" table at lines 23-36 and the `core/pattern-overrides` subsection at lines 172-214 (matches the plan's parenthetical line hints).
- `packages/block-library/src/cover/` has NO `README.md` (verified — only PHP/JS source, `block.json`, `editor.scss`, `style.scss`, etc.).
- `packages/block-library/CHANGELOG.md` exists with an `## Unreleased` heading at line 3 (matches the plan's target).
- A repo-wide sweep for `core/cover` in `docs/` confirms the bindings reference is the only canonical surface that enumerates supported blocks/attributes for bindings; the other mentions (curating-the-editor, block-filters reference, data-core-block-editor, testing-overview, static-dynamic-rendering) are unrelated to bindings (block-locking templates, render-callback example, test fixture, getElementParents example) and do not require updates.
- `docs/reference-guides/core-blocks.md` is autogenerated from `block.json` (the plan correctly skips it).
- The `block_bindings_supported_attributes` filter is documented only in `block-bindings.md` (single source of truth — no duplicate prose surfaces to keep in sync).

Task acceptance is drift-resistant: every task names a concrete audience, traces to specific spec requirements (with one minor citation slip in Task 4 — see Notes), and uses user-observable contract language (i18n message string, named UI controls, `backgroundType: "embed-video"` short-circuit) rather than implementation details (no PHP function names, no hook names, no filter names in the acceptance bullets). The plan stays strictly within doc scope — no code tasks duplicate code-plan responsibilities. Pattern Overrides is correctly headlined per spec, and the `__default` wildcard shape is the right idiom for the new Cover example (spec Glossary confirms the editor writes this shape, even though the existing paragraph example in the doc still uses the older per-attribute shape — a stylistic inconsistency the doc-writer can leave alone since updating the paragraph example is out of scope).

## Notes (non-blocking, doc-writer's discretion in phase 5)

These observations do not block approval but the doc-writer should weigh them when executing the plan:

1. **Task 4 trace citation slip.** Task 4 traces to "Spec Req 38 (PR shape — the changelog entry is part of the standard PR shape for block-library changes)". Req 38 is actually "The net diff (including tests) SHOULD target under ~500 lines" — it is about diff size, not changelogs. The stronger justification (which the task already invokes) is the `AGENTS.md` "each package has README.md and CHANGELOG.md" convention plus the `packages#maintaining-changelogs` link at the top of the file. The CHANGELOG entry is correct to include; only the spec-requirement citation is misattributed. The doc-writer can ignore this and add the entry on convention grounds alone.

2. **Task 3 enumerates "three round-trip states" — spec Req 24 has four.** The acceptance bullet says "The reader-takeaway paragraph names the three round-trip states the spec enumerates: insert pattern instance (renders the default), override per instance, reset (returns to default)." Spec Req 24 actually enumerates four states (a) default no override, (b) overridden, (c) reset-to-default, (d) reset affordance suppressed when value matches default. The three "render" states the plan names are correct as user-takeaway pedagogy (state (d) is a control-state, not a render-state), but for accuracy the doc-writer may want to either say "the three render states" explicitly or mention the disabled-reset semantics briefly.

3. **Version annotation.** The existing `block-bindings.md` uses inline "Since WordPress 6.9" annotations (e.g. lines 90, 218) for new bindings affordances. The plan's Task 2 Goal mentions "from WP 7.1 onward" but the acceptance doesn't require a version annotation. The doc-writer should add a "Since WordPress 7.1" annotation to the Cover-specific notes for consistency with the section's existing convention — this is a minor pattern-matching call, not a defect in the plan.

4. **Pre-existing pattern-overrides example uses per-attribute shape.** The existing paragraph example at `block-bindings.md:188-200` uses `metadata.bindings.content.source: core/pattern-overrides`, NOT the `__default` shape. The plan's Task 3 asks the new Cover example to use `__default`, which is correct per spec Glossary. The doc-writer should NOT feel obliged to also update the paragraph example — that is a separate concern out of this PR's scope, and the plan correctly does not ask for it.

5. **Parenthetical line numbers in Tasks 1/2/3.** The plan parenthetically cites line ranges ("currently at lines 23-36", "lines 172-214"). These are presented as hints, not locators — the load-bearing locators are header names ("Compatible blocks and their attributes section", "core/pattern-overrides subsection"). If an unrelated PR lands first and the line numbers drift, the doc-writer's header-based locating still works. No action required.

None of these is a blocking issue. The plan is ready for phase 5.
