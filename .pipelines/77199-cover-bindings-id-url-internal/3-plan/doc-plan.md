# Doc Plan: Cover block bindings — internal-only `id` and `url`

Spec: `<artifacts>/1-spec/spec.md` (approved)
Design: `<artifacts>/2-design-doc/design-doc.md` (approved)
Code plan: `<artifacts>/3-plan/code-plan.md` (approved)

All AC-N, Req-N, DC-N, OQ-N citations resolve to those documents.

## Overview

The code work lands Block Bindings support on `core/cover` for the `id` and `url` attributes, restricted to internal media library attachments, with Pattern Overrides as the headline use case. The only **author-facing** reference documentation that today enumerates which blocks and attributes participate in Block Bindings (and in Pattern Overrides by extension) is `docs/reference-guides/block-api/block-bindings.md`. That single file needs the Cover row added to its compatibility table, and a short Pattern-Overrides-on-Cover note explaining the internal-media constraint, the auto-hidden controls, and the embed-video carve-out — so a plugin/theme developer reading the bindings reference can correctly reason about what is supported on Cover before they ship a pattern or a custom source. The autogenerated `docs/reference-guides/core-blocks.md` is rebuilt from `block.json` and does not need a manual edit. There is no per-block `README.md` for `core/cover` (verified) — Cover's documentation surface is entirely the bindings reference guide. The package-level `packages/block-library/CHANGELOG.md` carries a release-notes entry under its `Unreleased` heading. Backport-changelog and PR-description metadata are already covered by Code-plan Task 13 and are NOT duplicated here.

A reviewer of this plan should sweep for any other text in the repo that today says "Cover does not support bindings" or enumerates the set of bindable blocks. The grep performed during planning surfaced exactly one such surface: `docs/reference-guides/block-api/block-bindings.md` (the "Compatible blocks and their attributes" table). All other appearances of "Cover" / "core/cover" in `docs/` (curating-the-editor README, block-filters reference, data-core-block-editor reference, testing-overview, RN integration test guide, the autogenerated `core-blocks.md`) are unrelated to bindings and do not need updating.

**Files**:

**Depends on**: Code-plan Task 1 (the `role: "content"` schema change) and Code-plan Task 2 (the `block_bindings_supported_attributes` filter that makes `core/cover` allow-listed at runtime).

**Traces to**: Spec Req 1, Req 2, Req 8; AC-1; Design §2.2, §6.1 Part 1, §8.

**Acceptance**:

### Task 2: Document the internal-media constraint and auto-hidden controls for Cover

**Goal**: Explain, in the Block Bindings reference, the Cover-specific behaviour that is NOT shared by other bindable blocks: the binding only honours media-library attachments (external URLs are surfaced as unresolvable), and several Cover-specific controls (parallax, repeat, media-replace, "Use featured image") are hidden whenever a binding is active. A reader who binds `core/cover` for the first time should not be surprised by the behaviour described in the spec's Acceptance Criteria.

**Audience**: Plugin and theme developers writing or shipping custom binding sources whose values may flow into `core/cover`, and pattern authors who bind Cover via Pattern Overrides.

**Files**:
- `docs/reference-guides/block-api/block-bindings.md` — MODIFY: add a new subsection within the document explaining the Cover-specific contract.

**Sections / scope**:
- A new H3 subsection placed within or immediately after the "Compatible blocks and their attributes" section (the doc-writer chooses the most natural anchor — adjacent to the table is fine; a small "Block-specific notes" or "Cover block" subsection is fine).
- The subsection covers, at minimum:
  - The internal-media-only invariant: bound `url` must resolve to a media-library attachment whose `id` is also bound from the same source instance. External URLs / mismatched sources are treated as unresolvable.
  - What "unresolvable" looks like to the end user in the editor (the spec's stable test-observable signal — the i18n message string) and what the front-end renders in that state (no `<img>`).
  - The controls that are hidden in the editor when a binding is active: parallax, repeat, media-replace, "Use featured image". A bound Cover surfaces overrides through the binding source (e.g. Pattern Overrides), not through the Cover's own media-replace control.
  - The render-time effective dim ratio when the stored `dimRatio` is the default 100 — the rendered overlay is non-opaque so the bound image is visible.
  - The embed-video carve-out: `backgroundType: "embed-video"` short-circuits the binding-aware paths in both editor and server; binding rows MAY appear in the UI but have no runtime effect on embed-video covers.

**Depends on**: Task 1 (the row that establishes Cover as bindable); Code-plan Tasks 6–9 (the editor-side behaviour the subsection describes); Code-plan Task 5 (the server-side render path the subsection references when describing front-end output).

**Traces to**: Spec Req 4, Req 5, Req 6, Req 7, Req 14, Req 16, Req 20, Req 22, Req 25, Req 26, Req 27; AC-4, AC-5, AC-6, AC-11, AC-12, AC-13, AC-14, AC-15, AC-16, AC-21; Design §5.4, §5.5, §10, §12 (embed-video carve-out).

**Acceptance**:
- A reader of the Block Bindings reference can answer "what happens if I bind Cover's url to an external (non-media-library) URL?" without leaving the page — the section names the user-visible affordance the spec defines and states that the front-end omits the `<img>`.
- A reader can answer "which Cover-specific controls disappear when a binding is active?" — parallax, repeat, media-replace, and "Use featured image" are all named.
- A reader is told that `backgroundType: "embed-video"` covers do not engage the binding-aware paths, even if the bindings UI lists `id`/`url` as bindable.
- The section explains that the default `dimRatio` of 100 does not produce a fully opaque overlay on bound covers — the rendered overlay remains visibly translucent over the bound image.
- The section does NOT prescribe internal implementation details (no `useEffect`, no filter names, no PHP function names) — it describes user-observable contract only.
- The section's wording is consistent with the surrounding doc's tone and the existing `core/pattern-overrides` subsection (descriptive prose plus optional small code/markup example).

### Task 3: Document the Pattern Overrides on Cover example

**Goal**: Give pattern authors a copy-pasteable example of binding a `core/cover` block via `core/pattern-overrides` (the headline use case for this PR). The existing `core/pattern-overrides` section in the bindings reference shows a paragraph example only; a Cover example is the natural counterpart for the new compatibility row.

**Audience**: Pattern authors creating synced patterns with overridable cover images.

**Files**:
- `docs/reference-guides/block-api/block-bindings.md` — MODIFY: add a Cover-on-Pattern-Overrides example inside the existing `### core/pattern-overrides` subsection (currently at lines 172–214), OR as a continuation of the Task 2 "Block-specific notes" / "Cover block" subsection — the doc-writer chooses the placement that minimises duplication.

**Sections / scope**:
- A short HTML/block-markup example showing a Cover block whose `metadata.bindings` is set to the `__default: { source: 'core/pattern-overrides' }` shape (the Pattern Overrides idiomatic form the spec's Glossary describes).
- A one-paragraph reader-takeaway: pattern authors mark Cover overridable the same way they mark paragraphs/headings overridable; per-instance overrides flow through the existing Pattern Overrides mechanism; reset semantics use the existing toolbar control (disabled when value matches default, per OQ-2).
- Cross-link or breadcrumb to the Task 2 "internal media required" affordance so authors know what happens when a Cover instance's override resolves to no usable attachment.

**Depends on**: Task 2 (the Cover-specific notes section sets the stage for the example); Code-plan Task 2 (the server-side allow-list registration that makes "Enable overrides" appear on Cover); Code-plan Task 12 (the e2e test that exercises this exact round-trip — the example should reflect the same authoring path the e2e walks through).

**Traces to**: Spec Req 9, Req 24; AC-2, AC-7, AC-8, AC-9, AC-10; Design §5.6, §9.

**Acceptance**:
- A reader can copy the example markup and use it (as written or as a starting point) to create a synced pattern with a bound Cover block.
- The example uses the `__default` wildcard shape (`metadata.bindings.__default = { source: 'core/pattern-overrides' }`) consistent with how the editor writes Pattern Overrides bindings, NOT a verbose per-attribute shape — readers should not learn an obsolete idiom from this doc.
- The reader-takeaway paragraph names the three round-trip states the spec enumerates: insert pattern instance (renders the default), override per instance, reset (returns to default).
- The example does not show external-URL binding (out of scope) and does not show mismatched-source binding (unsupported).
